# RERA-05: Adversarial UX pass (second pass)

Issue: [krisjughead-sys/Rera_Project#7](https://github.com/krisjughead-sys/Rera_Project/issues/7). This pass tried to misread the first-pass screens as a hurried buyer, a hostile promoter and a careless developer would. All examples are synthetic. Each finding records the attempted misreading, what the first draft did, the revision, and where the revision is now enforced (spec section, prototype, or test).

Severity: **High** = a buyer could act on a false belief about a real project; **Medium** = confusion likely but recoverable; **Low** = polish.

## Findings not fixed in this pass

- **Real-portal label text is unconfirmed.** Row labels in the spec ("Proposed completion (as registered)", "Revised proposed completion", "Extension of registration") are buyer-facing paraphrases. The official label text must be read first-hand (RERA-02 section 9) before the first real record is shown; the label mapping should then be recorded next to the field definition.
- **"Older snapshot" window of 90 days is a prototype constant**, not an official cadence. It must not be presented as derived from the quarterly-update duty until that order is read.
- **No notification channel.** "Return later" is browser-local only. Any push or email design needs an account and consent decision from the owner.

## Method note

One bounded design pass and one adversarial pass, as the issue budget allows, followed by one revision commit for the independent review. Screens were not regenerated; revisions were applied to the spec, the prototype and the test together so that a later change to one is caught by the other two. The prototype logic now lives in `core.js` so the tests exercise the real render functions rather than the source text.
